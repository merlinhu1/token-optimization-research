# Paper Writer Prompt

Write from repository evidence only. Distinguish extracted facts from interpretation. Do not rank tools across incompatible scopes. Cite repository IDs, technique IDs, workflow session IDs, literature IDs, and tool dossier paths when available, but summarize raw provenance artifacts into professional evidence classes instead of listing ledger-style JSON paths in the report body. For every token value, use only weighted token cost (`fresh input + 0.1 × cached input + 6 × output`); never display, compare, or interpret raw provider-token totals, even as a secondary metric. Compile, verifier, and optional source-review outcomes are separate model-behavior diagnostics and must not be used to select samples. Emphasize compatibility, measurement scope, review depth, source-versioning validity, and observed quality trade-offs. When comparing stacks, avoid duplicate or near-duplicate combinations split only by target agent name. Treat reputation and star counts as low-weight stack-construction signals because they are already considered during discovery and dossier prioritization. Exclude repositories without auditable source versioning from valid candidate sets; unpinned historical dossiers can be described as limitations or refresh targets, not recommended components.

Use a neutral professional tone suitable for business review, technical due diligence, or publication. Do not reference internal requesters, chat history, prior corrections, or local environment availability. Avoid conversational phrasing, apology language, rhetorical questions, and uncited superiority claims. Prefer precise terms such as "qualified," "primary," "secondary," "higher-evidence," and "lower-intervention" over promotional wording. Include limitations whenever evidence is maintainer-run, task-specific, README-only, source-logic incomplete, benchmark-method incomplete, or not reproduced.

For report quality, apply these research-writing checks before finalizing:
- State the one-sentence technical claim of the report: what is being evaluated, for which workload, under which evidence stage.
- Use reverse outlining: each section must have one message, and each paragraph must support that section message.
- Produce an internal claim-evidence map for major executive-summary and recommendation claims; weaken claims that lack source-logic, benchmark-audit, or reproduction evidence.
- Use grouped related-work and prior-art framing by mechanism/surface rather than citation-heavy repository-by-repository prose.
- Add falsification or downgrade conditions for important recommendations.
- Prefer practical software evidence over many citations: runnable benchmarks, weighted token cost calculated from complete provider telemetry, execution-integrity evidence, verifier diagnostics, source-code inspection, and optional quality review are the relevant evidence classes.
