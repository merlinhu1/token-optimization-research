# Research roadmap

## Current state

The current execution contract is Lifecycle V2 across Fastify and Beets: 6 bounded defect repairs per lane, each restoring one named behavior a specific upstream test decides, under authentic semantic regressions, normal software-engineering prompts, and lenient controller-only acceptance. Every task compiles and also runs one narrow essential-behavior smoke. Fastify requalified on 2026-08-21 against the repaired prompts; Beets was repinned to 746cecf2 and requalified on 2026-08-22.

The previous provider-backed Lifecycle V1 corpus was archived before rerun because model-facing prompts and shared prompt/configuration identity changed. The archive contains 103 historical sessions, their comparisons, and superseded protocols. They remain immutable evidence for the prior bytes and are not current controls.

Both lanes now carry provider-backed results under the current contract. Four interventions were tried against the Beets lane's earlier 22-31% spread -- shared code region, matched task count, prompt precision, and a repin onto a seed-size-bounded task set -- and the first three did not narrow it; the repinned lane has since been measured directly. Further provider work must be fresh and bound to the current Lifecycle V2 qualification hashes. The forward model policy is GPT-5.6 Sol/medium for Codex CLI and OpenCode, and direct-Anthropic Claude Opus 5/medium for Claude Code. High effort is retired for new work because excess deliberation can increase trajectory divergence.

Registry counts, role splits, and runtime splits live in the generated corpus summary in the top-level [`README.md`](../../README.md) rather than being restated here. What that summary cannot say is what the numbers currently support:

- **The three runtimes are not interchangeable controls.** On Fastify each holds baselines whose weighted token cost differs by more than any treatment effect measured so far, so a treatment is only ever read against a baseline from its own runtime. The cross-runtime numbers describe the runtimes, not the tools.
- **Every treatment here is a screen, not an effect estimate.** Caveman, ponytail, RTK, Serena, and Snip each hold one replicate per lane on each of Claude Code and Codex; CodeGraph likewise holds one replicate per lane on each of Claude Code and Codex. Under [ADR 0009](../architecture/decision-records/0009-replicate-counts-are-chosen-not-registered.md) a single replicate can support "worth carrying forward" and cannot support a ranked effect size. Nothing here is yet a ranking, and no two tools may be ordered against each other at these counts.
- **Caveman and ponytail changed weighted cost in opposite directions on the two runtimes, and that is still the strongest pattern in the corpus.** On Claude Code both tools came in below the whole retained baseline range on both lanes: caveman Fastify 543,826 and Beets 342,202, ponytail Fastify 547,110 and Beets 340,309, against baselines of 609,877/657,436 and 478,129/444,683. On Codex neither did: caveman Fastify 830,055 and Beets 711,158 both above the whole baseline range, ponytail Beets 634,381 above it, ponytail Fastify 740,600 inside the 727,939-822,709 spread and therefore indistinguishable from baseline at these counts ([ADR 0007](../architecture/decision-records/0007-ranked-reporting-and-median-sampling.md)). Two unrelated products reproducing the same sign flip points at the runtime rather than at either product. No result from either tool may be reported as its effect without naming the runtime it came from.
- **RTK breaks that pattern, and it is the first tool here to come in below the whole retained baseline range on Codex.** Codex Fastify 687,513 sits below the entire 727,939-822,709 baseline spread and Codex Beets 514,682 below the entire 564,733-614,214 spread, -9.2% and -16.2% against their paired r0s. Its Claude Code half is the weaker one: Fastify 647,992 lands inside the 609,877-657,436 baseline spread and is therefore indistinguishable from baseline at these counts ([ADR 0007](../architecture/decision-records/0007-ranked-reporting-and-median-sampling.md)), while Beets 394,584 is below both retained baselines (478,129/444,683) at -17.5%. So the caveman/ponytail sign flip is a property of those two tools, not a law of the runtimes: a third product ran the other way round.
- **The two RTK halves are different integrations, not the same treatment on two runtimes.** Codex runs `terminal-rtk-codex-instructions-v1`, a product-authored AGENTS.md/RTK.md instruction layer; Claude Code runs `terminal-rtk-claude-code-hook-v1`, the native PreToolUse hook. Both are guide-faithful canonical installs of the same product, but the surfaces differ more than caveman's or ponytail's do across runtimes, so an RTK Codex-versus-Claude-Code gap confounds runtime with integration surface and cannot be attributed to either alone.
- **Explicit adoption tracked the surface almost perfectly.** Under the Codex instruction layer the model wrapped essentially everything it ran — 30 of 31 shell commands on Fastify and 36 of 37 on Beets carried an `rtk` prefix (`rtk git`, `rtk sed`, `rtk rg`, `rtk npm`, `rtk uv`). Under the Claude Code hook it wrapped almost nothing explicitly — 0 of 29 foreground commands on Fastify (one backgrounded shell piped through `rtk grep`) and 7 of 24 on Beets. That is expected rather than anomalous: the hook rewrites below the model-visible command surface, so explicit invocation counts bound natural use under the instruction profile and say little about the hook profile ([ADR 0005](../architecture/decision-records/0005-token-accounting-and-protocol-identity.md)).
- **RTK did not land where caveman and ponytail did, which weakens the shared-lane suspicion below.** On Claude Code Fastify it is 18-19% above both of them (647,992 vs 547,110/543,826) and on Beets 16% above (394,584 vs 340,309/342,202). A third product run through the same Claude Code treatment lane landing well outside their cluster is evidence against the cluster being an artifact of the lane itself — though it does not rule one out, since RTK installs a different surface there than either of them.
- **On Claude Code the two tools landed almost on top of each other, which is a reason for suspicion rather than for confidence.** Caveman and ponytail are within 0.6% of each other on both lanes (547,110 vs 543,826; 340,309 vs 342,202) and within one step on trajectory length (52 vs 52; 35 vs 36). That is far tighter than the Claude Code baselines agree with each other. Two unrelated products converging that closely is more consistent with the Claude Code treatment lane differing from the baseline lane for something common to both runs than with two tools independently producing the same effect. Do not read it as agreement between the tools until a second replicate per profile says whether the gap is stable.
- **Claude Code Beets task-04 yields no verdict on either side of any pair.** All five retained Claude Code Beets sessions — both baselines, caveman, ponytail, and RTK — exit the `beets-membership-query-hashable-v2` verifier with the identical pytest collection error (`OSError: could not get source code` raised from the fixture's own `test/conftest.py` parametrize-id hook), so the verifier never judges the repair. Codex and OpenCode never hit it on the same lane. The pairs therefore still compare equal attempted work, and the earlier reading of this as the treatment doing less work was wrong; what it actually flags is a runtime-dependent fixture defect worth diagnosing before this lane carries more weight.
- **On Claude Code the two cost factors moved against each other for caveman and ponytail, and RTK is the first treatment to move them the other way.** For caveman and ponytail steps fell well below baseline while weighted cost per step rose (caveman Fastify 52 steps at 10,458 and Beets 36 at 9,506; ponytail Fastify 52 at 10,521 and Beets 35 at 9,723; against baselines of 71 at 9,260 and 66 at 6,738), so the totals fell on trajectory length rather than on cheaper steps. RTK Fastify ran 74 steps at 8,757 — slightly more steps than baseline at a lower cost per step, the only Claude Code treatment lane so far where the per-step factor fell — while RTK Beets ran 50 steps at 7,892, cutting trajectory length and paying more per step. On Codex neither factor moved the caveman/ponytail way: caveman Fastify ran 72 steps at 11,528 and ponytail Fastify 68 at 10,891, against baselines of 69-76 steps at 9,972-10,970, so trajectory length stayed in the baseline band and cost per step did the moving. The r0 baselines predate the step instrumentation, so these step figures compare a treatment r0 against a baseline r1.
- **Across RTK's four lanes the factor doing the saving is not consistent, which is the main reason to distrust the mechanism story.** Codex Fastify saved on trajectory length — 64 steps against a 69-76 baseline range, at 10,742 per step inside the 9,972-10,970 baseline band. Codex Beets saved on step price instead — 7,682 per step below the whole 8,824-9,597 band, at 67 steps just above the 63-64 range. Claude Code split the same way but with the lanes swapped. A terminal-output compactor should lower the price of a step; that it does so on only two of four lanes, and lowers step count on the other two, means the totals are not yet explained by the mechanism the product describes. One replicate per lane cannot tell that apart from ordinary trajectory variance.
- **Serena's Claude Code half is the largest weighted-cost drop in the corpus so far, and it is the first treatment whose two lanes differ mainly in how much the model actually called the tool.** Fastify came in at 528,151.8 over 72 steps, below the entire 609,877.0-657,436.2 baseline range at -13.4% against its paired r0. Beets came in at 270,645.0 over 45 steps, below the entire 444,682.9-478,129.1 baseline range at -43.4% — the largest single-lane drop measured yet, well past RTK's -17.5% on the same lane. Both pairs pass the apparatus-divergence check against their own runtime's baseline, and Beets task-04 failed the same conftest collection error as every other retained Claude Code Beets session, so the pairs still compare equal attempted work.
- **The size of the drop tracks explicit tool use, not just presence of the MCP server.** Fastify called `mcp__serena__*` twice in 64 total tool calls (`initial_instructions`, one `replace_content`) against 39 Bash, 10 Grep, 7 Read, 6 Edit; steps held flat against baseline (72 vs 71 r1) and the entire saving is a per-step price drop, 7,335.4 against 9,259.7 r1, -20.8%. Beets called `mcp__serena__*` thirteen times in 37 total tool calls — six `find_symbol`, five `replace_content`, one `insert_after_symbol`, one `initial_instructions` — against only 13 Bash, 9 Grep, 2 Read; there both factors moved, steps falling from 66 (r1) to 45 (-32%) and per-step price falling from 6,737.6 to 6,014.3 (-10.7%). A symbolic-navigation tool that gets used enough to replace most of the model's own search should look exactly like this: fewer, cheaper steps once real navigation happens, and only a price effect when it barely does.
- **Serena's Codex half reproduces the caveman/ponytail sign flip, and it is the cleanest adoption contrast in the corpus: zero explicit calls.** Codex Fastify came in at 763,068.8 over 68 steps, inside the 727,939.0-822,708.8 baseline spread and therefore indistinguishable from baseline at these counts ([ADR 0007](../architecture/decision-records/0007-ranked-reporting-and-median-sampling.md)). Codex Beets came in at 707,191.4 over 73 steps, above the entire 564,733.2-614,214.4 spread, +25.2% against its paired r1. All six verifiers passed on both lanes — including Beets task-04, which Codex clears and Claude Code does not — so these pairs compare equal completed work with no missing verdicts. Across both lanes the model made **no** `serena` tool calls at all: 38 shell commands and 6 file changes on Fastify, 42 and 6 on Beets, and every "serena" string in the event stream is the lane directory path rather than an invocation. The MCP handshake passed at setup with all 23 tools listed, so this is non-adoption under a working integration, not a broken one.
- **Taken together, Serena's two halves are the corpus's strongest link between adoption and direction, but they do not isolate the cause.** The tool went well below baseline on the runtime where the model called it (2 and 13 calls) and landed at-or-above baseline on the runtime where it called it zero times, which is what a retrieval tool that is paid for in context and only repays when used should look like. What the pair cannot separate is why adoption differed: the Claude Code profile installs Serena's product-authored native surfaces (MCP plus hooks/skills/plugins/rules) while the Codex profile is the official `setup codex` MCP registration, so runtime and integration surface move together exactly as they do for RTK. Whether GPT-5.6 Sol simply ignores an available MCP server that Opus 5 reaches for, or whether the Claude-side product guidance is what drives the calls, needs an ablation that holds one of the two fixed.

- **Snip's Claude Code half splits by lane, and its Beets verifier outcomes are an artifact that must not be read as quality.** Fastify came in at 706,765.2 over 89 steps, above the entire 609,877.0-657,436.2 baseline range at +15.9% against its paired r0, with all six verifiers passing on both arms. Beets came in at 433,184.0 over 51 steps, below the entire 444,682.9-478,129.1 range at -9.4%. The Beets comparison record shows `treatment_tasks_passed: 0` against a baseline's 5, and that number is **not** a verdict on the repairs: the final controller verifier could not spawn `pytest` for any of the six tasks (`Failed to spawn: pytest ... No such file or directory`). The agent itself ran pytest successfully in all six tasks and reported real suite results (2597 passed at one point), having built its own `workspace/.venv` after a bare `uv sync --offline --frozen` in task-01 — the fixture's dependency command is `uv sync --group test --frozen` — left the fixture venv without the test group the controller verifier depends on. So the lane measured a complete six-task trajectory whose repairs were never scored. The token sample is retained and valid under the disclosure policy; the quality column for Beets is simply empty, as it is for Claude Code Beets task-04 for an unrelated reason.
- **Snip moved the two cost factors in opposite directions on the two lanes, which is the same inconsistency that undercuts RTK's mechanism story.** Fastify ran 89 steps at 7,941.2 against baseline r1's 71 at 9,259.7: per-step price fell 14.2%, which is exactly what a terminal-output compactor should do, but the trajectory ran 25% longer and the total rose anyway. Beets ran 51 steps at 8,493.8 against 66 at 6,737.6: trajectory fell 23% while per-step price rose 26%. A compactor that lowers step price on one lane and raises it on the other, while step count moves the opposite way each time, is not yet explained by its stated mechanism. As with RTK's Claude Code hook, explicit adoption is uninformative here — zero `snip` invocations appear in either event stream, which is expected of a PreToolUse hook that rewrites below the model-visible command surface ([ADR 0005](../architecture/decision-records/0005-token-accounting-and-protocol-identity.md)).

- **Snip's Codex half is the strongest single result in the corpus, and the only tool whose mechanism reproduces cleanly across both of its lanes.** Codex Fastify came in at 590,513.2 over 86 steps, below the entire 727,939.0-822,708.8 baseline range at -22.0% against its paired r0 — the lowest weighted cost of any Codex Fastify session retained, baselines and every other treatment included. Codex Beets came in at 567,730.2 over 75 steps, inside the 564,733.2-614,214.4 spread and therefore indistinguishable from baseline at these counts ([ADR 0007](../architecture/decision-records/0007-ranked-reporting-and-median-sampling.md)), -7.6% against its paired r0. All six verifiers passed on both lanes, so both pairs compare equal completed work.
- **What makes the Codex half coherent is that both factors moved the same way on both lanes, unlike Snip on Claude Code or RTK anywhere.** Weighted cost per step was the lowest of any retained Codex session on both lanes — 6,866.4 on Fastify against a 9,971.8-10,970.4 baseline band and a next-best treatment of 10,742.4, and 7,569.7 on Beets against an 8,824.0-9,597.1 band. Step count rose above the baseline band on both (86 against 69-76; 75 against 63-64). So the tool reliably makes each step cheaper and reliably needs more of them; on Fastify the price win dominates, on Beets the extra steps cancel it out. That is a mechanism doing the same thing twice with different arithmetic, which is a materially better basis for a second replicate than a tool whose factors swap sign between lanes.
- **Snip's operation on Codex is evidenced indirectly, and the assignment proof should be read as installation-level.** The lane installed the pinned 0.24.1 release against verified artifact and guide hashes, wrote `hooks.json` and `config.toml`, and recorded `hooks_enabled: true`; the effective config carried both `[features].codex_hooks` and the current `[features].hooks`, so the deprecation warning Codex emits once per task is about the legacy key being present, not about hooks being off. But no compaction receipt appears in the event stream, zero explicit `snip` invocations occur, and the largest captured command output was 346,420 characters un-truncated — consistent with a hook that rewrites what reaches the model rather than what the controller records, and therefore not by itself proof of compaction ([ADR 0005](../architecture/decision-records/0005-token-accounting-and-protocol-identity.md)). The per-step drop below the whole baseline band on both lanes is the actual behavioural evidence that it operated. Codex's deprecation of `codex_hooks` is also a live maintenance risk: when the legacy key is removed, a profile relying on it alone would silently run as a baseline.

- **CodeGraph is the first Claude Code treatment to land above the whole baseline range on a lane, and that is useful evidence against the shared-lane suspicion above.** Claude Code Fastify came in at 571,489.9 over 58 steps, below the entire 609,877.0-657,436.2 baseline range at -6.3% against its paired r0. Claude Code Beets came in at 536,563.5 over 52 steps, above the entire 444,682.9-478,129.1 range at +12.2% — the highest weighted cost of any retained Claude Code Beets session, baselines included, and the highest cost per step at 10,318.5. Every other tool measured on that lane (serena, ponytail, caveman, RTK, snip) came in below both baselines. A sixth product running through the identical Claude Code treatment lane and finishing worse than baseline is hard to reconcile with the lane itself systematically flattering treatments, which is the main alternative explanation still open for the caveman/ponytail cluster. Beets task-04 failed the same `test/conftest.py` `pytest_make_parametrize_id` `OSError: could not get source code` defect as every other Claude Code Beets session, so that pair compares equal attempted work.
- **CodeGraph breaks the adoption-tracks-direction reading that Serena suggested.** The model called `mcp__codegraph__codegraph_explore` exactly five times on each lane — 5 of 47 tool calls on Fastify, 5 of 41 on Beets — so adoption was identical while the sign of the effect flipped. Serena's two halves differed in both adoption (2 versus 13 calls) and direction, which made adoption a tempting single explanation; CodeGraph holds adoption fixed and still splits, so at these counts adoption cannot be the whole story. Both lanes moved the factors the same way — fewer steps at a higher price, 58 against 71 at 9,853.3 against 9,259.7 on Fastify, 52 against 66 at 10,318.5 against 6,737.6 on Beets — and the +53% per-step jump on Beets is what a graph-retrieval tool returning large payloads into context would look like. What differs between the lanes is how much trajectory saving that price buys, not how often the tool was reached for.

- **CodeGraph's Codex half produced the most expensive treatment lane in the corpus, and the access path — not the product — is what differed.** Codex Fastify came in at 784,096.2 over 71 steps, inside the 727,939.0-822,708.8 baseline spread and therefore indistinguishable from baseline at these counts, +3.6% against its paired r0. Codex Beets came in at 1,016,469.0 over 78 steps against a 564,733.2-614,214.4 spread, +65.5% against its paired r0. Its 13,031.7 cost per step is the highest of any retained session on any runtime. All six verifiers passed on both lanes, so both pairs compare equal completed work and the cost is not bought with skipped effort.
- **The two CodeGraph halves used entirely different surfaces, and the call records show it rather than leaving it to inference.** On Claude Code the model called the MCP tool `mcp__codegraph__codegraph_explore` five times per lane and invoked the CLI zero times. On Codex it made zero MCP calls and instead ran `codegraph explore` as a shell command, eight times on Fastify and seventeen on Beets. So the profile's model-runtime PATH gate is load-bearing rather than belt-and-braces: it is the surface the Codex model actually reached for, and without it that arm would have been MCP-only against a model that used MCP not once. This is the same runtime-versus-integration-surface confound already noted for RTK and Serena, except here it is directly observable in the event stream.
- **Cost tracked graph payload volume, and the relationship is steeply non-linear.** Each `codegraph explore` returned roughly 20,000-23,000 characters, capped near 25,200: 184,063 characters total across Fastify's eight calls and 344,764 across Beets' seventeen. Payload roughly doubled between the lanes while the excess over baseline grew about fifteen-fold, from +27,140 to +402,255 weighted tokens. That shape is what retrieved payload persisting in a re-sent context should produce, since each call is paid for again on every subsequent turn rather than once. One replicate per lane cannot separate that mechanism from ordinary trajectory variance, but it is the most directly instrumented cost story in the corpus so far and the cheapest to test: a replicate that varies explore count would confirm or kill it.

- **jCodeMunch's Claude Code half is the largest weighted-cost drop in the corpus on both lanes, and the model called it zero times.** Fastify came in at 524,327.7 over 86 steps, below the entire 609,877.0-657,436.2 baseline range at -14.0% against its paired r0, and the lowest weighted cost of any retained Claude Code Fastify session, baselines and every other treatment included. Beets came in at 259,926.1 over 50 steps, below the entire 444,682.9-478,129.1 range at -45.6% -- the largest single-lane drop measured here, past Serena's -43.4% on the same lane -- with a cost per step of 5,198.5, the lowest of any retained Claude Code session. All six Fastify verifiers passed. Beets task-04 failed the same `test/conftest.py` `pytest_make_parametrize_id` `OSError: could not get source code` as every other Claude Code Beets session, verified in this run's own verifier output, so that pair compares equal attempted work at 5 of 6 on both arms.
- **The mechanism is not adoption, and this is the corpus's sharpest counterexample to reading direction off adoption.** The event stream contains no `mcp__jcodemunch__*` call and no skill invocation on either lane: 36 Bash, 15 Grep, 11 Read and 6 Edit on Fastify, 13 Bash, 13 Grep, 8 Read and 7 Edit on Beets. This is non-adoption under a working integration rather than a broken one -- the MCP handshake returned its tool list before the first prompt, and Claude Code's own session-init event lists `jcodemunch` among registered skills, so both surfaces were present and reachable. Serena suggested that use predicts direction and CodeGraph showed adoption held constant while the sign flipped; jCodeMunch drops cost furthest of anything measured while using nothing at all, so at these counts explicit adoption does not explain direction in either direction.
- **The one structural difference from every other Claude Code lane is the hook layer, and it is a candidate rather than a finding.** jCodeMunch is the only Claude Code profile here running with `hooks_enabled: true`: its official installer writes PreToolUse, PostToolUse, PreCompact, SessionStart, TaskCompleted and SubagentStart hooks alongside the MCP registration, in advisory mode, since `--strict` was not passed. The cost shape is what a below-the-surface intervention should produce -- fresh input roughly halved on both lanes, 248,379 against a 401,794-410,220 baseline band on Fastify and 140,668 against 281,607-341,266 on Beets, while cached input rose on Fastify. But no hook receipt, `hookSpecificOutput`, or `additionalContext` marker appears anywhere in either event stream, which is expected of hooks that act below the model-visible command surface and is therefore not evidence that they fired ([ADR 0005](../architecture/decision-records/0005-token-accounting-and-protocol-identity.md)). One replicate per lane cannot separate a hook effect from trajectory variance. The cheapest test is a hooks-disabled ablation against this same profile.
- **This lane is also the first jCodeMunch result whose installation matches the product's own Claude Code instructions.** Until 2026-08-28 the profile ran generic `init --client claude-code`, which cannot write the Claude Agent Skill bundle at all; `AGENT_INSTALL_UNIVERSAL.md` names `jcm install claude-code --skills` as the Claude Code command. The correction matters for this metric specifically, because the skill exists to let Claude load the policy on demand instead of carrying it in baseline context every turn, so the previous setup would have paid for that policy block on every turn. Read the numbers above as belonging to the corrected installation only; there is no earlier jCodeMunch result on this contract to compare them against.

- **jCodeMunch's Codex half reverses its own Claude Code result, and it does so with heavy adoption rather than none.** Codex Fastify came in at 842,293.4 over 106 steps, above the entire 727,939.0-822,708.8 baseline range at +11.3% against its paired r0. Codex Beets came in at 843,529.4 over 100 steps, above the entire 564,733.2-614,214.4 range at +37.3%. All six verifiers passed on both lanes -- including Beets task-04, which Codex clears and Claude Code does not -- so both pairs compare equal completed work and the cost was not bought with skipped effort.
- **Put beside its Claude Code half, jCodeMunch is the corpus's clearest evidence that adoption does not predict direction.** The same product, on the same two fixtures, dropped 14.0% and 45.6% below baseline on Claude Code while calling its tools **zero** times, and rose 11.3% and 37.3% above baseline on Codex while calling them 50 and 49 times. Serena's pair suggested that use predicts saving; CodeGraph held adoption fixed and still split; jCodeMunch runs the relationship backwards on both halves at once. Whatever explains these two sign flips, at these counts it is not how often the model reached for the tool.
- **The Codex calls are real work through a deliberate dispatcher, not handshake noise.** jCodeMunch exposes one MCP tool, `order`, that routes an `action` argument to the underlying operations, so a single schema sits in context instead of roughly thirty. Under it Fastify ran 9 `search_text`, 8 `get_file_outline`, 8 `get_symbol_source`, 6 `plan_turn`, 6 `assemble_task_context` and 6 `register_edit`; Beets ran 11 `get_file_outline`, 7 `get_symbol_source`, 6 `plan_turn`, 6 `register_edit`, 5 `search_symbols`, 5 `search_text` and 2 `find_references`. Returned payload totalled 159,965 characters on Fastify and 216,152 on Beets against 24 and 21 shell commands, so retrieval genuinely displaced shell work and was then paid for in every subsequent re-sent turn.
- **Both Codex factors moved the same way on both lanes, which makes this a coherent mechanism rather than variance.** Weighted cost per step fell below the entire baseline band on both -- 7,946.2 against 9,971.8-10,970.4 on Fastify and 8,435.3 against 8,824.0-9,597.1 on Beets -- while step count rose far above it, 106 against 69-76 and 100 against 63-64. The tool reliably makes each step cheaper and reliably needs many more of them, and here the extra steps dominate. That is the same shape as Snip's Codex half with the arithmetic landing the other way, and it is a better basis for a second replicate than a tool whose factors swap sign between lanes.
- **The declared warm-index state is nominal on the Codex lane, and that is a protocol defect rather than a result.** The controller builds the index before the run, but the model's first `resolve_repo` used a relative path, which the server itself warns resolves against its own working directory; it reported the repo unindexed under a different key, and the model then ran a full `index_folder` of its own on both lanes (`performed_incremental: false`, 320 files/7,090 symbols and 344/7,476). So this arm measured a cold-start index built inside the session while the profile records `tool_state: warm-index`. It costs steps and context on the treatment side only, and it should be fixed before any jCodeMunch replicate: either pass an absolute path at warmup so the keys match, or drop the warm-index claim for this profile.

- **TokenJuice's Claude Code Fastify lane is the most expensive session in that lane's corpus, and it is the first treatment here whose compaction can be seen working.** Fastify came in at 946,588.8 over 110 steps, above the entire 609,877.0-657,436.2 baseline range at +55.2% against its paired r0, with all six verifiers passing on both arms. Unlike Snip, whose Codex hook left no compaction receipt anywhere, TokenJuice writes a visible marker into the command output the model receives: `[tokenjuice] This is the complete, authoritative output for this command. It was deterministically compacted…` appears 30 times against 67 Bash calls, so roughly 45% of shell outputs were compacted in-band. That is direct evidence of operation rather than the installation-level inference every other hook profile has had to settle for.
- **It is also the cleanest case of a compactor doing its job and costing more anyway.** Weighted cost per step fell to 8,605.4 against the 9,259.7 of the instrumented r1 baseline, -7.1%, which is what compacting 45% of shell output should do. But the trajectory ran 110 steps against 71, +55%, and the step count swamped the per-step saving. The mechanism is not in question here the way it is for Snip or RTK; what is in question is why a shorter per-step context produced a much longer trajectory. That is the pairing worth a second replicate, because if it reproduces it is an argument that terminal compaction can cost more precisely when it works.

The incident, including the partial spend it consumed, stays disclosed in [`tokenjuice-claude-code-beets-r0-session-limit-20260829.json`](../../sources/evaluations/audits/tokenjuice-claude-code-beets-r0-session-limit-20260829.json), which is now the only record of it. This is an interrupted execution, not a replicate dropped for the number it produced. The r0 slot for that pool is now occupied, so a repeat Beets measurement runs at r1.

- **TokenJuice's Codex half reverses its Claude Code Fastify result and lands almost exactly where Snip's did.** Codex Fastify came in at 616,397.2 over 78 steps, below the entire 727,939.0-822,708.8 baseline range at -18.6% against its paired r0. Codex Beets came in at 593,330.4 over 69 steps, inside the 564,733.2-614,214.4 spread and therefore indistinguishable from baseline at these counts ([ADR 0007](../architecture/decision-records/0007-ranked-reporting-and-median-sampling.md)), -3.4%. All six verifiers passed on both lanes. Snip, the corpus's other terminal-output compactor, produced the same shape on the same runtime: a large Fastify win (-22.0%) and a Beets result inside the spread (-7.6%). Two independent products on the same surface class reproducing that split is the first cross-tool pattern here that is not a sign flip.
- **TokenJuice's cost factors are not consistent across its lanes, and the Beets r1 that arrived last corrected an earlier reading here.** With the Beets half missing this section claimed the per-step factor fell on every lane and only trajectory length disagreed. It does not. Three of four lanes drop per-step cost -- 8,605.4 against 9,259.7 on Claude Code Fastify, 7,902.5 against a 9,971.8-10,970.4 band on Codex Fastify, 8,599.0 against 8,824.0-9,597.1 on Codex Beets -- but Claude Code Beets moves the other way, 7,803.0 against 6,737.6, a 15.8% rise, while its trajectory falls from 66 steps to 54. That is the same inconsistent-factor pattern that already undercuts the mechanism stories for RTK and Snip, and TokenJuice is not exempt from it.
- **What does track the factors is how much the compactor actually did.** Claude Code Fastify carried the `[tokenjuice]` marker on 30 of 67 Bash calls, 45%, and its per-step cost fell. Claude Code Beets carried it on 4 of 28, 14%, and its per-step cost rose. A compactor that fires on nearly half of shell output lowering step price, and one firing on a seventh failing to, is at least the right shape for a dose-response relationship. It is two points on one runtime and confounded with the fixture, so it is a hypothesis to test with a forced-compaction-rate ablation rather than a finding.
- **The same product leaves a compaction receipt on one runtime and none on the other, and that is a recording artifact rather than a behavioural one.** On Claude Code the `[tokenjuice]` marker is written into the output the model receives, 30 times against 67 Bash calls. On Codex the identical product produces zero markers, yet `tokenjuice doctor codex` reports `health: ok`, the effective config carries the current `[features].hooks = true` rather than a deprecated key, and the installed command is `tokenjuice codex-post-tool-use`. Recorded command output is if anything slightly *larger* than baseline there (2,243,604 characters against 2,225,430 on Fastify), which is what a PostToolUse hook that rewrites what reaches the model while the controller records the pre-hook stream should look like ([ADR 0005](../architecture/decision-records/0005-token-accounting-and-protocol-identity.md)). Codex-side operation is therefore evidenced at installation level plus the per-step drop, not by a receipt; do not read the two halves as differing in what the tool did.

- **With both halves in, TokenJuice and Snip agree in sign on all four runtime-by-fixture cells, which is the strongest cross-tool result in the corpus.** Claude Code Fastify: Snip +15.9%, TokenJuice +55.2%, both above the whole baseline range. Claude Code Beets: Snip -9.4%, TokenJuice -11.9% against the same r0, both below it. Codex Fastify: Snip -22.0%, TokenJuice -18.6%, both below the whole range. Codex Beets: Snip -7.6%, TokenJuice -3.4%, both inside the spread and therefore indistinguishable from baseline at these counts. Two independently authored terminal-output compactors reproducing the same four signs, and near-identical magnitudes on Codex, is a much better argument that the effect belongs to the surface class than any single tool's pair. It also means the Claude Code Fastify penalty is not a TokenJuice quirk: whatever makes a shell compactor expensive on that lane hits both products.
- **TokenJuice's Claude Code Beets r1 completes the pair its r0 could not.** It came in at 421,362.4 over 54 steps, below the entire 444,682.9-478,129.1 baseline range, -5.2% against the r1 baseline and -11.9% against r0. Task-04 exited with the same `test/conftest.py` `OSError: could not get source code` as every other Claude Code Beets session, verified in this run's own verifier output, so the pair compares equal attempted work at 5 of 6 on both arms. It reuses the r0 protocol identity, since the apparatus did not change; only the interrupted replicate did.

a hooks-disabled ablation of jCodeMunch on Claude Code, because it is now the largest drop in the corpus, its only structural difference from every other Claude Code lane is a hook layer whose operation is unevidenced either way, and a single ablation would either establish the mechanism or kill it; a replicate that varies CodeGraph's `explore` call count on Codex Beets, because the payload-to-cost relationship there is the most directly instrumented mechanism claim available and a single lane cannot distinguish it from trajectory variance; a second replicate of Snip on Codex, because it is now both the largest measured effect here and the only one whose two factors reproduce in the same direction across its lanes, which makes it the cheapest one-sample claim to either harden or dissolve; an ablation that separates runtime from integration surface for Serena, since it has the largest adoption-linked spread in the corpus and a one-line explanation that is currently confounded; a fixture guard that prevents an agent's own `uv sync` from stripping the test group the controller verifier needs, because Snip's Claude Code Beets lane spent a full six-task budget and bought no quality verdict at all, plus a check that a hook profile fails closed rather than silently degrading to baseline if Codex removes the deprecated `[features].codex_hooks` key; a second replicate per profile per runtime, because the caveman/ponytail sign flip, their convergence, RTK's and Snip's inconsistent cost factors, and Serena's zero-adoption Codex half are all one-sample claims that a second sample would either harden or dissolve; and a diagnosis of the Claude Code Beets task-04 collection error, because a lane with a verifier that cannot return a verdict under one runtime is measuring less than it appears to.
