The runtime decides whether a token-saving tool saves tokens.

Fifteen products, measured one at a time against matched controls on two real repositories and three coding-agent runtimes. In 12 of 26 comparisons that exist on more than one runtime, the same product changes the direction of its effect when the host agent changes.

Read the technical report See the results

Every value on this page is weighted token cost (fresh input + 0.1 × cached input + 6 × output), measured against that runtime's own bare control on the same repository. No raw-token result is shown. This is a screening study, not a leaderboard — most cells hold a single replicate.

The host agent matters as much as the tool.

The same integration can cut weighted token cost on one runtime and raise it on another. Caveman costs 9.7% and 20.6% more on Codex, saves 25.0% and 32.1% on Claude Code, and is indistinguishable from the control on OpenCode. Serena costs more on both Codex lanes and saves about a quarter on both Claude Code lanes. This is the central result, and it is why a single-runtime recommendation is not supportable from this corpus.

The repository matters too

Nine of thirty-one product–runtime pairs change direction between the two fixtures alone. SigMap on Claude Code saves 18.6% on Fastify and costs 51.8% more on Beets. A product evaluated on one repository has not been evaluated.

Claude Code is where these products pay

Ten of thirteen reduce cost on both Claude Code lanes. On Codex only five of fifteen do, and several are substantially more expensive — CodeGraph reaches +72.4% on Beets.

Savings can carry a cost

LeanCTX's OpenCode integration denies the agent's native file tools. It is the largest saving measured — and the only arm that reproducibly loses a task its control always passes. Reported as an association, not a demonstrated mechanism.

Coverage is uneven, and that is stated rather than smoothed.

The Codex and Claude Code arms are the result of this study. The OpenCode arm is an early screen: three of its sixteen runnable profiles have been measured, and it is labelled preliminary everywhere it appears.

Codex CLI — 15 products

Complete, with Headroom excluded on resource grounds by owner direction. Controls: 3 replicates per repository.

Claude Code — 13 products

Near-complete. Controls: 5 replicates on Fastify, 6 on Beets — the deepest control pool in the corpus.

OpenCode CLI — 3 of 16

Preliminary. Thirteen profiles unrun. Snip and Token Savior have no runnable OpenCode profile at all, so this arm cannot mirror the Codex sweep even with unlimited budget.

Read the boundary before the headline.

What this study does not establish, stated as plainly as what it does.

  • It is not a leaderboard. Most cells hold one replicate. A single replicate can support “not worth carrying forward”; it cannot support a ranked effect size.
  • The deeper arms are a selected sample. Products that screened well were resampled; products that screened badly were not. More replicates is not evidence of a better product.
  • Overlapping ranges mean indistinguishable, and are reported that way rather than ordered.
  • Mechanism is not isolated. Interception, retrieval depth, persistent instructions, tool schemas and trajectory length are all plausible contributors; this design separates none of them.
  • Effect sizes do not transfer across runtimes. A Claude Code figure is not an estimate of the same product's Codex or OpenCode figure.
  • Correctness is reported, not averaged away. 693 of 726 task outcomes passed; the exceptions are attributed individually in the report.

Inspect the evidence.

Every figure on this page is reproducible from the machine authority in the repository. Invalidated runs, exclusions and disclosed spend that bought no measurement are published alongside the results.
