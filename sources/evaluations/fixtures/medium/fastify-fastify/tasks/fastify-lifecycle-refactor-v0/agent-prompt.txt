Refactor Fastify's Content-Type parsing using the prescribed solution below. This is a controlled token-usage workload: follow the recipe directly rather than exploring alternate cache designs.

Repeated calls to `ContentType.from(...)` with the same raw header must reuse one shared, bounded parsed representation while preserving parsing and serialization behavior.

## Implementation recipe

1. Change only `lib/content-type.js` for this task.
2. Import `LruMap` from `toad-cache` as `Lru` and create one module-level cache with capacity `100`.
3. Expose that cache through `static get cache()` on `ContentType`.
4. In `ContentType.from(headerValue)`, return `cache.get(headerValue)` when present; otherwise construct one `ContentType`, store it under the exact raw header string, and return it.
5. Do not write a second cache implementation or alter media-type normalization, parameter parsing, serialization, request parsing, structured `+json`, or reply charset behavior.

## Validation recipe

The container cannot bind listening sockets. Use in-process checks only.

- Run `node -c lib/content-type.js`.
- Run `node --test test/content-type.test.js`.
- Run a short `node` assertion that `ContentType.from(raw) === ContentType.from(raw)`, `ContentType.cache` exists, the media type is lowercased, parameters are preserved, and serialization round-trips.
- Do not run broad Fastify suites.

## Stop condition

Stop when `lib/content-type.js` uses the shared bounded `LruMap`, the focused content-type tests pass, and identity reuse is proven. Preserve task 1 and ignore unrelated later-task failures.
