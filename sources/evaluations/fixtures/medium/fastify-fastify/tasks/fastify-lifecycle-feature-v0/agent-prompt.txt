Implement the missing Fastify request-metadata feature using the prescribed solution below. This is a controlled token-usage workload: follow the recipe directly rather than rediscovering the architecture.

Expose the parsed media type through the exact public property `request.mediaType` and the corresponding `FastifyRequest.mediaType` type. The value must be the normalized media type, such as `application/json`, consistently available before and during body validation. Do not introduce `request.contentType`.

## Implementation recipe

1. In `lib/request.js`, import `./content-type` and add a `mediaType` getter to `Request.prototype`. Parse `this.headers['content-type']` with `ContentType.from(...)`; return its normalized `.mediaType` only when the parsed representation is valid, otherwise return `undefined`.
2. In `lib/validation.js`, use `request.mediaType` as the body content-schema key. Remove the duplicated `getEssenceMediaType` helper and its header reparsing.
3. In `types/request.d.ts`, add `readonly mediaType: string | undefined` to `FastifyRequest`.
4. Do not add a second public API, parser, or normalization path. `lib/handle-request.js` should retain its existing parser flow; no new request symbol is required.
